## Scope and changed expectations

- Capture loss is retained as source-frame intervals and epoch offsets, independent of transcription success. Small gaps remain exact-zero unavailable frames; a contiguous unavailable run exceeding ten seconds is represented by an unfilled epoch jump instead of an arbitrarily large silence allocation. Source loss never becomes recovered merely because batch ASR succeeds.
- One shared `QualityRecord` holds at most **64 epochs and 256 spans**. Omitted spans retain class/resolution-aware counts; omitted epochs and saturated counters prevent unwarranted completeness or exact availability claims. The mandatory private sidecar is bounded to **256 KiB** and remains independent of optional evidence collection. Recording retention/discard removes it and its registered transaction files together with the recording.
- The full sidecar/checkpoint is authoritative. Frontmatter uses the same record type with an explicitly labelled **48 KiB projection** when needed, retaining all epochs and omission totals; the existing **64 KiB prefix** limit is unchanged. Body markers use the full record. The maximum-width fixture serializes to **67,958 bytes** before projection and **49,065 bytes** afterward. Metadata-only refresh preserves body bytes and inode using bounded shifts; it shares the existing in-place rewrite interruption window and does not claim atomic replacement.
- The existing retry job is armed before initial batch ASR so the original backend survives a pre-checkpoint crash. A genuinely fresh batch and a first live-to-batch fallback retain **six total attempts** (the former inline initial attempt plus five retries). Existing active/claimed jobs preserve their stored budgets; five-attempt retry jobs stay at five. Deduplication preserves claimed state, attempts, due time, budget, and original backend. Unknown or changed automatic origins refuse before staging, decoding, or hosted finalization. Explicit manual local redo remains a separate authorized operation; an existing valid filing checkpoint requires no ASR.
- Changed-rate capture uses the fixed initial retained rate and a bounded off-callback normalizer; unchanged-rate PCM is bit-identical. AEC algorithms/defaults are unchanged. Availability is reapplied after filter output/tail. Offline AEC refuses when omitted source losses or saturated accounting prevent exact masking, allowing the existing raw fallback to preserve zeros.

See the [quality model](../crates/corti-core/src/quality.rs), [durable store](../crates/corti-core/src/quality_store.rs), [capture normalizer](../crates/corti-core/src/capture_normalizer.rs), and amendments in [ADR 0010](../design/adr/0010-live-inbox-filing.md) and [ADR 0014](../design/adr/0014-transcript-generation-provenance.md).

`fresh_constructor` includes construction; `warm_primed` uses a 100 ms untimed prefix on the same instance. Both include finish/drop, and timed warm output includes explicitly counted pending prefix frames. Code paths are primed before measurement: neither mode means a cold process or cold cache. These measurements impose no machine-speed threshold and measure neither HAL/AEC/disk/full-graph real-time behavior nor ASR quality or process memory. No production optimization is justified by this table alone.

## Explicit local redo evidence and authorization

After normal successful job/checkpoint cleanup, a recording may retain an immutable outstanding tee-loss snapshot while historical backend authority is unavailable. A user-requested whole-file local redo can recover that processing loss without asserting a historical backend. The private CLI settlement helper is called only after whole-file transcription returns `Ok`; it checks the actual backend identity and durable storage, then selects the distinct nonserialized `ExplicitLocalWholeFileSuccess` outcome. Source-loss and source/storage uncertainty remain incomplete or unknown. Default/`--aws` redo with unknown origin still refuses before execution, and no note-read API or origin rewrite is added.

The portable harness at `/tmp/corti-redo-recovery-harness` extracts the actual CLI guards, settlement helper, and tests, with actual checkpoint/private-file/store/queue implementations. Its platform/backend enum seam does not execute ASR or establish native app compilation. `/tmp/corti-162-explicit-local-redo-before.log` records the behavioral failure under the previous origin-match-only settlement: after Done cleanup/reopen, tee-only quality still required batch recovery. `/tmp/corti-162-explicit-local-redo-after.log` records all three extracted CLI checks passing, including the strengthened existing default/AWS zero-call guard. The new core uncertainty/failed/partial control test is recorded in `/tmp/corti-162-explicit-local-redo-core.log`; the full quality-model module passes **25/25** in `/tmp/corti-162-explicit-local-redo-quality-suite.log`. Core all-target/all-feature strict Clippy and extracted CLI strict Clippy pass in `/tmp/corti-162-explicit-local-redo-{core,cli}-clippy.log`.

The three new explicit-local functions are included in the CLI/core groups above. The existing CLI backend-guard test was strengthened rather than counted again.
